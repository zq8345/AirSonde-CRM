## 1. 现在 Joe 要点几步才能回一封信

逐行读了前端（`public/index.html:3092` `toolDraftReply`），真实路径：

| 步 | 动作 |
|---|---|
| 1 | 进「已回复」页（数据源 `/api/leads?group=replied`，**每行一个线索**，不是每行一封回复） |
| 2 | 找到那条线索，**勾选复选框**（必须且只能勾 1 条，勾 2 条会被拒绝） |
| 3 | 点工具栏「起草回复」 |
| 4 | 前端拉**全量** `/api/replies`，在浏览器里过滤出这条线索的、取最新一封 |
| 5 | 等 AI 起草 **10–20 秒** |
| 6 | 弹窗显示草稿 |
| 7 | **手动复制** |
| 8 | 切到自己的邮箱 → 找到那个会话 → 粘贴 → 改 → 发 |
| 9 | 回到后台**手动标记**状态 |

**结论：9 步，且第 8 步离开了系统。**

### 这不是推测——库里有铁证
`replies` 表里 **#4 / #5 两条的正文就是**：
> `（在 邮件 上回复了，由人工标记）`（长度 17 字符）

**Joe 已经在用自己的邮箱回信、回来打卡记账。** 系统在回复这一环上**事实上已被绕过**，只剩记账功能。这是本方案最硬的需求证据。

### 三个具体的坏点
1. **看不到客户到底说了什么。** 起草弹窗只展示 `r0.summary`（AI 摘要），**不展示回复原文**，更不展示我们发出去的原信。
2. **回复列表根本不存在。** 「已回复」页是**线索列表**，一行一个公司，只挂一条最新摘要。一个公司回了 3 封（Campervanbuilders 就是 #7/#10 两封+）只能看到最后一条。
3. **AI 起草是「一次性弹窗」**，关掉即消失、不入库、不能改、不能存。下次要再等 10–20 秒重生成。

### 从真数据得出的四条硬需求（凭空设计想不到）
1. **降噪是第一职责**：15 封里 **4 封机器噪音 + 2 封测试数据**，真正要人处理的只有 **9 封**。回复箱首先要把这 6 封挡在视线外，而不是排版更好看。
2. **必须并排显示我们发出去的那封原信**：#10「number 8 we would be interested in」——没有原信，Joe 看不懂客户在说什么。
3. **必须剥离引用与签名**：#13 正文 1105 字符，真实内容只有 `Yes, I would be interested.`，其余是 `On Sat, Jul 25... Tejoy <hello@tejoy.net> wrote: > Hi team, > I'm following up...`；#10 长度 **4000（撞上截断上限）**，真内容一句话。不剥离，列表里全是我们自己发出去的信。
4. **意向类里 4 封明确索要「目录/报价」**（#3 #6 #7 #9 有 3 封直接要 catalog+pricing）——这是**同一个动作**，值得做成一个按钮，而不是每次让 AI 从头写。

### 一个我本来怀疑、核完发现是错的判断
#6 与 #14 开头几乎一样（都是 "Thank you for reaching out and for sharing information about…"），却被判成 `interested` / `not_interested` 相反两类。我原以为是 AI 分类不可靠，**拉原文核对后发现两次都判对了**（#6 后半索要 catalogue，#14 明说 "we're not looking to add any new suppliers"）。
→ **AI 分类可信到足以驱动界面分组。** 不需要为"分类不准"做额外设计。

## 3. 方案

### 3.1 回复列表长什么样
**一行一封回复**（不是一行一个线索），默认按时间倒序，顶部四个分组页签：

| 页签 | 含谁 | 默认 |
|---|---|---|
| **🔥 待处理**（默认） | `interested` + `inquiry`，且未标记已处理 | ✅ 打开就在这 |
| 💤 已婉拒 | `not_interested` + `complaint` | |
| 🤖 自动/噪音 | 自动回执、调查问卷、测试数据 | 折叠 |
| ❓ 认不出主人 | `lead_id IS NULL`（孤儿，现有能力，并进来） | |

每行：`公司名 · 分类标签 · 剥离引用后的正文首行 · 收到时间 · [处理] 按钮`。

**降噪判定**（第一版用**保守规则 + 存证**，不上 AI）：
- 存量已有 `raw_headers` 全量头（当初就是为这个存的）→ 检 `Auto-Submitted:` / `X-Autoreply` / `Precedence: bulk` / `List-Id`；
- 加两条正文规则：`gorgias.com/satisfaction-survey` 这类调查链接、以及**同一发件人同一正文重复**（#1/#2 就是完全重复）。
- ⚠️ **只折叠不删除**，且分组可切回去看。判错了要能捞回来——漏一封真客户比多看一封机器信贵得多。

### 3.2 一键起草在哪触发
**点开一封回复 → 右侧详情面板直接开始起草**，不需要先勾选再点工具栏。

详情面板三段（自上而下）：
1. **客户原话**（剥离引用/签名后的正文，可展开看全文）
2. **我们上一封发的**（折叠，一点展开）← 解决 #10 那类"number 8"
3. **AI 草稿**（进面板即开始生成，10–20 秒；生成中显示进度而不是干等）

⚠️ **必须实时进度或流式**：现在是 10–20 秒黑盒等待。AI 类交互不给反馈 = 用户以为卡死。

### 3.3 发出去前怎么改
草稿框**可直接编辑**（textarea），下面两个按钮：
- **[复制并标记已回复]** —— 第一版**保持"人自己发"**，但把"复制"和"标记"合成一步，直接消灭 #4/#5 那种"回来补打卡"。
- **[存为草稿]** —— 草稿**入库**（现在关窗即丢，下次重烧 10–20 秒）。

> 🔴 **我不建议第一版做"系统直接发出"**：发信是不可逆动作，而回复涉及报价/承诺，措辞错了代价远高于开发信。先把"看得懂 + 起草快 + 状态自动记"三件做对，等 Joe 用顺手了再谈系统内直发。**这条请 Joe 拍**——若他明确要一键直发，技术上现成（`deliverEmail` 已具备），我按他的意思做。

**「发目录/报价」快捷动作**：意向类里 3 封直接索要 catalog+pricing，值得给一个预置模板按钮（一键把目录/价单话术填进草稿框），比每次 AI 重写快且稳定。

### 3.4 回完怎么记状态
- 点「复制并标记已回复」→ 自动写 `replies.handled_at` + 推进线索状态 + **停掉自动跟进**（避免客户已回信我们还在自动催，这是真实存在的尴尬）。
- 婉拒类一键「停跟进并归档」；#14 那种"keep on file"给一个**「N 个月后复访」**（复用现有 `next_action_date`）。

### 3.5 需要的数据改动（预估）
- `replies` 加两列：`handled_at`（处理时刻）、`is_noise`（降噪判定结果，**存判定不删数据**）。
- 新端点：回复列表（分组+分页+剥离引用）、标记已处理、存草稿。
- 起草复用现有 `/api/replies/:id/draft`（已存在，不重写）。
- 前端：「已回复」页从**线索列表**改成**回复列表 + 右侧详情面板**。

**改动面粗估**：后端 2 个迁移列 + 3 个端点；前端一个新页面骨架 + 详情面板。**不碰发信链路**。

## 4. 建议顺序（若总工过）
1. **降噪 + 一行一封的列表**（把 9 封真回复从 15 条里捞出来）——最快见效，且不依赖任何新交互。
2. **详情面板：客户原话 + 我们上一封原信**（解决"看不懂"）。
3. **起草入面板 + 可编辑 + 存草稿 + 流式/进度**。
4. **[复制并标记已回复] 一步到位**（消灭手动补打卡）。
5. 复访提醒、发目录快捷动作。
6. （待 Joe 拍）系统内直发。

## 5. 我不确定 / 需要 Joe 拍的
- **系统内直发 vs 复制到邮箱**（3.3）——我倾向第一版不做，理由是不可逆 + 涉及报价承诺。**这是产品判断不是技术判断，归 Joe。**
- **降噪规则的边界**：`other` 类里除了机器噪音，会不会有真客户？现有 15 封里 `other` 三封全是机器（2 封自动回执 + 1 封调查）。**样本太小，我不敢把 `other` 整类默认折叠** —— 方案里只折叠"命中明确机器特征"的，其余 `other` 仍留在待处理。
- **测试数据（#11/#12）怎么处理**：建议加个 `is_test` 手工标记，不自动判（自动判会误伤真客户）。
