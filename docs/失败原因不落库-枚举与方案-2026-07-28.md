**原始输出（9 张表）**

**对账命令**（一次查询取全部计数，避免分次查漏）
```sql
SELECT (SELECT COUNT(*) FROM emails WHERE status IN ('failed','bounced'))                     AS emails_failed_rows,
       (SELECT COUNT(*) FROM leads WHERE COALESCE(fetch_fail_count,0)>0)                      AS leads_fetch_failed,
       (SELECT COUNT(*) FROM leads l JOIN lead_analysis a ON a.lead_id=l.id
         WHERE COALESCE(l.fetch_fail_count,0)>0 AND a.reason LIKE '%抓不到%')                  AS leads_with_reason,
       (SELECT COUNT(*) FROM settings WHERE key LIKE '%fail%' OR key LIKE '%_run')            AS settings_fail_slots,
```

**原始输出**

### 结论表

| # | 位置 | 记了失败吗 | 记了原因吗 | 缺口（对账数） |
|---|---|---|---|---|
| 1 | **`emails.status ∈ (failed, bounced)`** | ✅ | ❌ **表里根本没有 error 列** | **89 / 89 无原因（100%）** |
| 2 | `leads.fetch_fail_count > 0` | ✅ 计数 | ⚠️ 部分：达上限才把原因写进 `lead_analysis.reason` | **149 中仅 80 有原因 → 69 条只有计数** |
| 3 | `settings.*_fail_last` / `*_run`（5 个键） | ✅ | ✅ 有原文 | ⚠️ **单槽覆盖：只留最后一条，历史全丢** |
| 4 | `lark_bitable_map` 同步失败 | ❌ 根本不记行 | ❌ | 失败即无痕 |
| 5 | `leads.status ∈ (bounced, blacklisted)` | ✅ | ❌ | 6 条无原因 |

⚠️ **第 2 条还有一个隐患**：失败原因被塞进 `lead_analysis.reason` —— 那个字段本意是"AI 为什么给这个分"。**用业务字段兼职存故障文本**，将来查任何一边都会混。

## 三、方案（与「平台错误不许被吞」是同一件事的两端）

**② 管当场可见（分类不吞），这条管事后可查（落库）。共用同一张关键词表，不做成两套。**

### 3.1 唯一的关键词表（单点、可审）
新建 `src/failkind.ts`，**只此一处**，不散在各个 catch：
```ts
// ⚠️ 这张表是"平台错误 vs 业务错误"的唯一判据。散在各处 = 漏一个它就会伪装成业务错误。
export const PLATFORM_PATTERNS: { kind: string; re: RegExp }[] = [
  { kind: "subrequest-limit", re: /too many subrequests/i },
  { kind: "cpu-limit",        re: /exceeded cpu|cpu time limit/i },
  { kind: "daily-limit",      re: /daily (request )?limit|error 1027/i },
  { kind: "rate-limit",       re: /rate.?limit|429/i },
  { kind: "quota",            re: /not enough credits|quota|insufficient/i },
];
export function classifyError(e: unknown): { kind: string; name: string; raw: string } {
  const name = String((e as any)?.name || "");
  const raw  = String((e as any)?.message || e || "");
  const hit  = PLATFORM_PATTERNS.find(p => p.re.test(raw));
  return { kind: hit ? `platform:${hit.kind}` : (name === "AbortError" ? "timeout" : "unknown"), name, raw };
}
```
⚠️ **`unknown` 是合法结果，且必须原样保留 raw** —— 关键词表一定会漏，**漏掉时要退化成"未知 + 原文"，不能退化成某个业务分类**。今天 `timeout-or-network` 就是这么把平台错误伪装成业务错误的。

### 3.2 `emails` 加 `error` 列
```sql
ALTER TABLE emails ADD COLUMN error TEXT;   -- 运行时/服务商**原话**，不存我们的措辞
```
- 由 `ensureEmailColumns()` 运行时幂等补（本仓已有先例：`reply-inbox.ts:ensureReplyColumns`），**不需要手工跑 DDL**。
- 写入点就是上面那两行，把已经在手里的原文一并写进去：
  `UPDATE emails SET status='failed', error=? WHERE id=?` ← `${kind} | ${name}: ${raw}`（截 500）
- ⚠️ **老数据不回填。** 89 条历史失败保持 `error IS NULL` = **"未知"**。
  **"未知"比"猜的"诚实** —— 回填等于伪造证据。
