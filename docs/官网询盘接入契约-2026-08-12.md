# 官网询盘 → CRM 管道 · 接入契约与简报（2026-08-12 · CRM 窗）

> 状态：**CRM 侧已实现并自测通过（15/15）**；⛔ **公开入口未开**（按派单：方案写清楚，不自己开）。
> 官网侧改动**不在本仓**，见 §4 给 Web 窗的片段——需总工派单给那边，本窗不越界改别人的仓。

## 1. 为什么是这个接法

官网表单的后端 `airsonde-web/functions/api/contact.ts` 是 **Pages Function（服务端）**，不是浏览器直投。
所以走 **Function 服务端转发 → CRM `/api/inbound`**：

- 浏览器全程不碰 CRM ⇒ 不需要 CORS、不需要把任何密钥发到前端
- CRM 端点复用现成管道（压制名单 → 去重 upsert → 飞书卡片），⛔ 不新写端点
- 官网现有的"推 Joe 飞书群"**保留不动**（双写：群里看得见 + CRM 里跟得住）

## 2. 契约（CRM 侧，已实现）

`POST {CRM_BASE}/api/inbound`，`content-type: application/json`

**请求头**
| 头 | 必需 | 说明 |
|---|---|---|
| `x-inbound-token` | 是（机器调用方） | 共享密钥。**未配 INBOUND_TOKEN ⇒ 一律 503**（fail-closed，不是放行）；不匹配 ⇒ 401 |
| `x-idempotency-key` | **是** | ≤80 字符 `[A-Za-z0-9_.:-]`。缺 ⇒ **400**（不静默降级：转发重试是常态，没有它会重复追加 notes / 重复推飞书） |

**请求体**（官网表单字段名可直接用）
```json
{ "company": "Acme Ltd", "name": "Jane", "email": "jane@acme.com",
  "phone": "+1 555 0100", "inquiry_type": "OEM / ODM",
  "message": "…", "source_form": "website_contact", "country": "us" }
```
- `company` / `company_name` 等价；两者皆空时用 `name` 兜底（leads 主展示字段不能空）
- `source_form` **只有带对 token 的调用方**能声明，且必须在服务端白名单内（现仅 `website_contact`）。
  自称白名单外的值 → 静默回落老规则，不报错。**理由**：Origin 和 body 都是调用方自称，
  只有密钥能回答"这真是我们自己的官网后端吗"（与 openrouter.ts 的来源背书同一条纪律）。
- `country` 走既有两位码白名单，非法 → null（不猜）

**响应**：`{ok:true}` · `{ok:true,idempotent:true}`（重放） · 400 / 401 / 503 / 429

**落库**：`source=website_contact` · `next_action=跟进官网询盘` ·
notes = `官网询盘 | 姓名 | 电话 | 类型 | locale | 留言`；同邮箱已存在则**追加 notes 不新建行**；
命中压制名单（退订/退信/投诉）**静默 ok、不入库不通知**（合规红线，与发信同一道闸）。

## 3. 与浏览器直投路径的关系

本 worker 自带的 `/catalog` 落地页仍可无 token 直投 —— **行为一字未动**（honeypot + 每 IP 限流 + 压制名单）。
两条路各判各的：token 路径按密钥认证，浏览器路径按老三件。

⚠️ **可信调用方豁免每 IP 限流**（不是开特例）：官网询盘全部经同一个 Pages Function 出口 ⇒ 对 CRM 是同一个 IP。
照原规则，官网询盘到 10 封/小时就会**静默不推飞书**、30 封直接 429 丢单，而现象是"Joe 没收到通知、系统一切正常"。
per-IP 在服务端转发这一跳上量的是错的东西；防刷留在官网侧（honeypot + Origin 校验）。

## 4. 给 Web 窗的对接片段（**本窗不改那个仓**）

在 `functions/api/contact.ts` 现有 Lark 推送**之后**追加（推 Lark 成功与否都转发；两条通道互不拖累）：

```ts
// env: CRM_INBOUND_URL, CRM_INBOUND_TOKEN（Pages 项目 secret，绝不进仓）
if (env.CRM_INBOUND_URL && env.CRM_INBOUND_TOKEN) {
  try {
    await fetch(env.CRM_INBOUND_URL, {
      method: 'POST',
      headers: {
        'content-type': 'application/json',
        'x-inbound-token': env.CRM_INBOUND_TOKEN,
        // 幂等键：同一封询盘重试要复用同一把键
        'x-idempotency-key': crypto.randomUUID(),
      },
      body: JSON.stringify({
        company, name, email, phone,
        inquiry_type: inquiryType, message,
        source_form: 'website_contact',
      }),
    });
  } catch { /* CRM 不可达不能让用户看到失败：Lark 已收到，询盘没丢 */ }
}
```
⚠️ 两点必须照做：① CRM 转发失败**不改**给用户的返回（Lark 那条已经保证询盘不丢）；
② 幂等键在重试时**复用同一把**（若将来加重试逻辑，键要在重试外层生成）。

## 5. 公开入口：三个方案（⛔ 本单只写清楚，不开）

现状：`crm.airsonde.com` 整站在 Cloudflare Access 门后，`workers_dev:false`，`API_HOST` 未配
⇒ **官网 Function 现在打不进来**（Access 在边缘就挡了，与 worker 里的路径豁免无关）。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. Access 服务令牌**（推荐） | Joe 在 Zero Trust 建 Service Token，给 `airsonde-crm` 应用加一条 Service Auth 策略；官网 Function 带 `CF-Access-Client-Id/Secret` 两个头 | **不开任何公开面**，CRM 继续整站在门后；机器身份由 CF 边缘验，我们的共享密钥作第二道 | 需 Joe 在控制台建令牌 + 加策略；官网侧多两个 env |
| B. 公开正门 `api.airsonde.com` | 配 API_HOST/PUBLIC_API_URL，custom_domain，只放 `/api/inbound` 等公开端点、其余 404 | 代码已支持（配变量即激活）；将来退订链接/webhook 也要它 | 多一个公开面，且该子域**绝不能**配 Access |
| C. 重开 workers.dev | `workers_dev:true` | 一行 | 公开面且域名难看，无独立价值 |

**推荐 A**：本单要的是"官网后端 → CRM"这一跳，A 恰好只解决这一跳而不引入公开面。
B 留给发信单（退订链接/Resend webhook **必须**公开可达，那时一并开，见 docs/发信通道选型）。

## 6. 部署前置（Joe/总工 动作）

1. 生成随机密钥（≥32 字节），`npx wrangler secret put INBOUND_TOKEN`（CRM 侧）
2. 同一把值配进官网 Pages 项目的 `CRM_INBOUND_TOKEN`；`CRM_INBOUND_URL=https://crm.airsonde.com/api/inbound`
3. 按 §5 选定的入口方案配好（A：建 Service Token + 策略；官网侧加两个 CF-Access 头）
4. 上线后端到端实测一次：官网表单真提交一次 → CRM 后台出现 `source=website_contact` 的线索
   （⚠️ 契约类改动必须真 curl 端到端验，桩只能证明"我以为的协议"）

## 7. 自测闸

```bash
npx wrangler dev --port 8791 --inspector-port 9341      # 另一个窗可能占着 8788
TOKEN=<本地 .dev.vars 里的 INBOUND_TOKEN> node scripts/inbound-selftest.mjs
```
覆盖：⓪进程身份（打的是不是本仓）· ①坏 token→401 / 未配→503 / 浏览器路径不变 · ②honeypot 不入库
· ③来源标记与白名单外声明不生效 · ④同键重放不重复 · ⑤缺幂等键→400。
⚠️ 不给 TOKEN 时会**明确列出跳过项**（跳过 ≠ 通过）。

## 8. 本单发现的两个既有缺陷（**已报总工，未修**）

1. 🔴 **搜索长串必 500**：`/api/leads?q=` 的 LIKE 模式超过约 48 字符 → `D1_ERROR: LIKE or GLOB pattern
   too complex`。**生产 D1 已实测同样报错**（CF API code 7500），不是本地假象。
   影响：后台搜索框粘一个长邮箱/长网址就 500。修法（未做）：q 截断到安全长度，或超长时改用 `=` 精确匹配。
2. 🔴 **目录抓取不受"零密钥锁死"约束**：`runNmeaDiscovery` / `runLinkHarvest` / `runDirectoryRefresh`
   不检查任何 key，cron 每 6 小时照跑 → 生产库已被灌入 242 条 Wanew 垂直（nmea 199 / rvwithtito 41）
   的无关线索，且在增长；同时反复爬第三方站。处置方案见发给总工的报告，**等裁定**。
